# 02_problem-observations.md

## 1. Windows 앱: MandroController

### 1.1 "왜 우리 앱을 써야 하는가?" : 단순 복제 프로토타입의 한계
* **[12/29 월요일] 관찰**: **CustomTkinter(CTk)**를 사용해서 기존 Third-party 프로그램(ComportMaster) 기능을 빠르게 옮겨놓은 첫 번째 프로토타입을 만들었음.
* **문제점**: 이 프로그램은 그냥 기능만 나열된 **모놀리식(Monolithic) 구조**라 파일 하나가 모든 걸 다 하고 있었고, 결정적으로 ComportMaster랑 비교했을 때 우리 앱만의 메리트가 전혀 없었음.
* **기술적 반성**: "이미 있는 서비스가 있는데 굳이 우리 걸 써야 할 이유가 없다면 만들 의미가 없다"는 게 내 개발 가치관임. 사용자에게 기존 기능 말고 새로운 가치를 제공할 방법을 찾아야 한다고 생각함. 그 과정에서 overview 페이지와 현재 상태 그래프 창을 고안하게 됨.

### 1.2 프레임워크의 한계와 실시간성 확보 실패
* **[12/30 화요일] 관찰**: UI를 좀 더 제대로 짜보려고 **Flet** 프레임워크로 갈아타는 시도를 함.
* **현상**: 로봇에서 쏟아지는 고속 시리얼 로그를 처리하는데 UI가 자꾸 멈추거나(Freezing), 렌더링 속도가 데이터 수신 속도를 못 따라가는 성능 병목이 생김. 백그라운드에서는 데이터를 받고 있는데 화면은 실시간으로 안 변하는 상황도 있었음.
* **영향**: UI 틀은 그럴싸하게 나왔지만, 제어 프로그램에서 '로그 멈춤'은 그냥 탈락임. 결국 성능 확실하게 보장되는 **PyQt6**로 다시 엎기로 함.

### 1.3 하드웨어 변수 발생과 CES 시연 통보
* **[12/31 수요일] 관찰**: PyQt로 한참 개발 중이었는데 갑자기 **6자유도(6-DOF)** 하드웨어가 추가됐다고 기기를 가져다주심.
* **문제점**: 하드웨어가 다양해지면 패킷 구조나 UI 대응 로직이 꼬이기 마련인데, 기존의 경직된 코드는 하나 고치면 다른 기능이 망가질 리스크가 너무 컸음.
* **긴급 상황**: 심지어 같은 날, 이 프로그램이 당장 다음 주 **CES 2026** 현장에서 시연용으로 쓰일 거라는 소리를 들음. 연습용/테스트용이 아니라 진짜 실전이었음.

### 1.4 하이 스테이크(High-stake) 상황과 물리적 제약
* **[1/2 금요일] 관찰**: 남은 개발 시간은 딱 하루. 근데 현장에서는 **양손 기기**를 동시에 써야 한다고 요구사항이 확정됨.
* **위기 상황**: 내 앞엔 5자유도/6자유도 왼손 기기 1개씩 뿐인데, 오른손 기기 없이도 양손 제어가 안정적으로 돌아갈 거란 걸 확신해야 했음. 보수적이고 견고한 아키텍처가 아니면 답이 없는 상황이었음.
* **영향**: 하루 만에 성능이랑 확장성 문제를 다 해결하려고, 그냥 기능 수정을 넘어서 **MVC 패턴 도입**하여 전체적으로 리팩토링함.

### 1.5 [추가] 인턴 종료 직전의 프로토콜 전면 수정
* **관찰**: 인턴 종료를 단 4일 앞두고, STAGE 단계를 없애고 명령을 한번에 보내기 위해서 또, 패킷의 길이를 단축시켜 연결의 안정성을 높이기 위해서 패킷 송수신 프로토콜이 아예 바뀌어버리는 상황이 발생함.
* **문제점**: 통신 규약이 바뀌면 데이터 파싱부터 UI 연동까지 코드 전반에 영향이 감. 특히 5-DOF와 6-DOF 기기에 따라 패킷 구조를 다르게 처리해야 했던 기존 방식은 이런 급작스러운 변화에 대응하기 매우 까다로웠음.
* **영향**: 하지만 미리 구축해둔 MVC 모델 덕분에 모델의 파싱 로직만 수정하여 예상보다 훨씬 빠르게 대응할 수 있었음. 또한, 이번 기회에 5-DOF/6-DOF를 통합 대응할 수 있는 단일 프로토콜로 정리하면서 코드의 복잡도를 획기적으로 낮출 수 있음을 확인함.

## 2. Android 앱: MandroController_Android

### 2.1 사용성 문제: 모바일 환경에 안 맞는 UI
* **관찰**: 윈도우 앱에 있는 정밀 제어 기능을 그대로 가져왔더니, 작은 터치 화면에서 슬라이더 하나하나 조작하는 게 너무 불편했음.
* **영향**: 밖에서 의수를 빠르게 써야 하는 사용자 입장에선 직관적인 '매크로' 중심의 UX가 꼭 필요하다는 걸 깨달음.

### 2.2 연결 안정성 및 데이터 휘발 문제
* **관찰**: 블루투스 연결할 때 앱이 죽거나, 고생해서 만든 커스텀 매크로가 앱 껐다 켜면 다 날아가는 현상이 보였음.
* **리스크**: 하드웨어 제어 앱에서 데이터 날아가는 건 사용자 신뢰를 완전히 깎아먹는 문제라 무조건 잡아야 했음.

### 2.3 피드백 시스템 부재
* **관찰**: 버튼을 눌렀을 때 명령이 기기에 제대로 들어갔는지 알 수 있는 방법이 눈으로 보는 것밖에 없었음.
* **현상**: 조작 확신이 없으니까 버튼을 자꾸 중복해서 누르게 되고, 이게 기기에 불필요한 과부하를 줄 수도 있겠다 싶었음.

### 2.4 윈도우/안드로이드 플랫폼 간의 통신 로직 이식
* **관찰**: 윈도우(Python)에서 검증된 제어 로직을 안드로이드(Kotlin)로 옮길 때, 하드웨어 종류의 차이와 프로그래밍 언어의 차이로 프로토콜의 **바이너리 데이터 처리(Endianness 등)**를 일치시키는 데 어려움이 있었음.
* **영향**: 윈도우 앱 리팩토링 과정에서 정립한 프로토콜 구조를 안드로이드에도 동일하게 적용하여 두 플랫폼 간의 제어 정밀도를 맞추는 작업이 핵심 과제가 됨.
