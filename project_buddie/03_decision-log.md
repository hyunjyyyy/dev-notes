# 03_decision-log.md

## 1. 전체 구조: 서버 없이 "파일 하나를 주기적으로 다시 만든다"
* **결정**: 수집기는 `docs/data/jobs.json` 한 파일만 만들고, 화면은 그 파일을 읽어 브라우저에서 모든 걸 처리한다. 서버 API도 DB도 두지 않는다.
* **판단 이유**: 공고 수가 1,000~2,000건이라 브라우저 메모리에서 필터·정렬이 즉시 됨. 갱신은 하루 두 번이면 충분하므로 실시간 쿼리가 필요 없음. 이 두 가지 가정이 서버를 없앨 수 있게 해 줬음.

---

## 2. 수집: Python 표준 라이브러리 + 정규식
* **결정**: `requests`, `BeautifulSoup`, `lxml` 같은 외부 패키지 없이 `urllib.request`로 받고 `re`로 파싱한다.
* **판단 이유**:
    * 출처가 전부 옛날식 JSP 게시판이라 서버가 완성된 HTML을 주고, 테이블 구조(`<tr>`/`<td>`)가 단순함. 브라우저 렌더링도 DOM 트리 탐색도 필요 없었음.
    * 외부 패키지가 없으면 Actions에서 `pip install` 단계, requirements 파일, 버전 충돌이 전부 사라짐. 몇 달 뒤 다시 돌려도 그대로 돔.
* **파싱 방식**: 센터 게시판은 행마다 들어 있는 `fnGoBoardSl('번호')` 호출을 정규식으로 잡아 게시글 번호를 얻고, 같은 행의 `<td>`를 순서대로 읽음. `to_text()`에서 `<br>`, `</tr>`, `</p>` 등을 줄바꿈으로 바꿔 본문을 텍스트로 만든 뒤 "접수", "마감" 같은 단어가 있는 줄을 그대로 보여줌(형식이 제각각이라 해석하지 않음).

## 3. 출처 플러그인 구조
* **결정**: 출처마다 `ID`, `NAME`, `HOME`, `collect(cache)`만 가진 모듈을 `scraper/sources/`에 두고, `main.py`의 `SOURCES` 목록에 넣으면 끝나게 한다. 재단 사이트면 `FOUNDATION = True`를 붙여 재단별 보기에 묶이게 한다.
* **판단 이유**: `02`에서 본 것처럼 "서울 공고 판별"부터 출처마다 다르니 공통 추상화를 억지로 만들지 않고, 각 모듈이 같은 모양의 dict 목록만 돌려주도록 계약을 최소로 잡았음. 첫날 출처를 2개에서 5개로 늘릴 때 `main.py`는 한 줄씩만 바뀜.
* **공통 유틸만 `common.py`로**: 서울 구 찾기, 마감 문구 뽑기, 재단 이름 찾기, 자유 서술 직종을 센터 게시판 직종명으로 맞추기(`job_of`). 재단 이름 사전(`FOUNDATIONS`)은 재단 사이트 출처의 `NAME`과 같게 둬서 센터 게시판 공고와 재단 사이트 공고가 한 묶음이 되게 했음.

## 4. 상세 캐시와 속도 제한
* **결정**: 상세 페이지는 처음 본 게시글만 받고 결과를 `data/detail-cache.json`에 저장해 커밋한다. 실행당 300건, 1초 간격. 목록에서 사라진 게시글의 캐시는 지운다.
* **판단 이유**: IP 차단(`02` Phase 2)을 피하면서도 하루 안에 신규 공고 상세가 채워지는 수치. 캐시를 Git에 커밋하면 Actions 실행 사이에 상태가 유지되고, 별도 저장소가 필요 없음.
* **실패 격리**: 한 출처가 실패하면 직전 결과를 그대로 두고 화면에 "실패"만 표시. 모든 출처가 실패했을 때만 종료 코드 1로 Actions를 빨갛게 만듦.

## 5. 저장: Git 저장소를 DB로
* **결정**: `jobs.json`과 캐시를 Actions가 `github-actions[bot]` 이름으로 커밋·푸시한다. `git diff --cached --quiet`로 바뀐 게 있을 때만.
* **판단 이유**: 하루 두 번 쓰기, 동시 쓰기 없음, 수 MB 크기. 이 조건이면 DB가 주는 건 비용과 권한 관리뿐임. 대신 모든 갱신이 히스토리로 남아서, 나중에 "중복이 기분 탓인가"를 어제 커밋과 비교해 바로 검증할 수 있었음(`02` Phase 4).

## 6. 자동화: GitHub Actions cron
* **결정**: `schedule`로 UTC 23:00, 09:00(KST 08:00, 18:00)에 실행. `workflow_dispatch`로 수동 실행. `concurrency` 그룹으로 겹침 방지, `timeout-minutes: 30`, `permissions: contents: write`만 부여.
* **판단 이유**: 공개 저장소면 무료이고 저장소 밖에 아무것도 만들 필요가 없음. 공식 액션 `actions/checkout@v4`, `actions/setup-python@v5` 두 개로 환경이 끝남.
* **알고 감수한 것**: GitHub 예약 실행은 예약 시각보다 수십 분 늦는 일이 흔함. 공고 갱신 용도에선 문제없다고 판단해 README에 적어 두는 것으로 끝냄.

## 7. 화면: 프레임워크 없는 HTML/CSS/JS
* **결정**: React·Vue 없이 `app.js` 한 파일(약 270줄)로 필터·정렬·렌더링을 처리. 빌드 도구 없음.
* **판단 이유**: 화면이 "목록 하나 + 필터"라 상태 관리 프레임워크의 이점이 거의 없고, 빌드가 없어야 `docs/` 폴더를 그대로 Pages에 올릴 수 있음.
* **세부 선택**:
    * `<template>`으로 카드 틀 재사용, `<details>`로 모바일에서 필터 접기.
    * CSS는 커스텀 속성(`--bg`, `--ink` 등)으로 색을 한 곳에서 관리하고 `clamp()`로 여백을 반응형 처리. 약 240줄.
    * 오늘 날짜는 `toLocaleDateString("sv-SE", { timeZone: "Asia/Seoul" })`로 구함. 스웨덴 로케일이 `YYYY-MM-DD`를 내놓는 걸 이용해 날짜 라이브러리 없이 KST 기준 문자열을 얻는 트릭.
    * 관심 어린이집은 이름의 포함 관계로 매칭("아모레퍼시픽"을 넣으면 "아모레퍼시픽 서울어린이집"도 걸리게).
* **폰트**: Pretendard Variable을 jsDelivr CDN의 dynamic subset으로. 한글 가독성이 좋고 필요한 글자만 내려받음. 프로젝트의 유일한 외부 의존.

## 8. 개인화: `localStorage`
* **결정**: 필터 상태와 관심 어린이집 목록을 브라우저에 저장. 저장 실패(사생활 보호 모드 등)해도 화면은 동작하도록 `try/catch`.
* **판단 이유**: 로그인·계정 없이 개인화하는 가장 싼 방법. 사용자가 사실상 한 명이라 기기 간 동기화가 필요 없었음.

## 9. 재게시 중복 제거 (2026-10-16)
* **결정**: 출처·어린이집·제목·직종·접수시작일이 같으면 가장 최근 게시글 하나만 남기고, 마감일은 묶음 중 가장 늦은 날짜로 둔다. 출처별 수집 결과마다 적용(`main.py`의 `dedupe`).
* **판단 이유**: `02` Phase 4에서 확인한 대로 id는 전부 다르니 내용 기준으로 묶어야 했음. 화면에서 묶어 "재게시 N회"로 보여주는 안도 있었지만, 데이터 자체가 깨끗한 게 이후 모든 기능에 유리하다고 봐서 수집 단계에서 처리. 2,050건 → 1,658건.
* **검증**: 남은 공고가 각 묶음에서 게시일·마감일이 가장 늦은 것인지 전수 확인, 예외 0건.

## 10. 보육교사만 수집 (2026-10-16)
* **결정**: `보육교사`, `가정보육교사`만 남기고 보조·대체교사, 조리원 등은 수집 단계에서 제외. 화면의 직종 필터는 삭제.
* **판단 이유**: 사용자가 안 볼 직종을 보여줄 이유가 없고, 센터 게시판은 목록 단계에서 직종을 먼저 걸러야 실행당 300건인 상세 요청 예산이 보육교사 공고에만 쓰임. 1,658건 → 1,022건.
