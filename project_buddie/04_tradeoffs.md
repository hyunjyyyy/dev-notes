# 04_tradeoffs.md: 선택과 포기

모든 선택의 기준은 하나였다. **의존성 0, 비용 0, 운영 0.** 아래는 그 기준 때문에 고르지 않은 것들과, 고른 것 때문에 포기한 것들.

## 1. 수집: 표준 라이브러리 + 정규식 vs requests/BeautifulSoup/Scrapy/Playwright
* **안 쓴 것**: `requests`(HTTP), `BeautifulSoup`·`lxml`(DOM 파싱), `Scrapy`(크롤링 프레임워크), `Playwright`(브라우저 자동화).
* **안 쓴 이유**: 출처가 전부 정적 HTML이라 브라우저가 필요 없고, 테이블 구조가 단순해 DOM 트리가 필요 없었음. 패키지 하나를 넣는 순간 `pip install`, requirements, 버전 고정이 따라옴.
* **얻은 것**: 설치 단계 없는 실행, 몇 달 뒤에도 그대로 도는 안정성.
* **포기한 것**: 사이트가 마크업을 바꾸면 정규식부터 깨짐. BeautifulSoup이었다면 선택자 하나만 고치면 될 일이 정규식 여러 개를 다시 맞추는 일이 될 수 있음.

## 2. 저장: Git 커밋 vs 데이터베이스/객체 저장소
* **안 쓴 것**: SQLite, PostgreSQL(Supabase 등), S3·R2 같은 객체 저장소.
* **안 쓴 이유**: 하루 두 번 쓰기에 동시 접근이 없고 크기가 수 MB. DB가 주는 건 호스팅 비용과 접근 권한 관리뿐이었음.
* **얻은 것**: 모든 갱신이 히스토리로 남음. 중복 분석 때 어제 커밋을 바로 꺼내 비교할 수 있었음.
* **포기한 것**: 갱신 커밋이 하루 두 개씩 쌓여 저장소가 계속 커짐. 쿼리를 못 하니 통계를 보려면 스크립트를 짜야 함. 동시 쓰기가 불가능해 수집기를 둘로 나눌 수 없음.

## 3. 스케줄: GitHub Actions cron vs 서버 cron/Lambda/Cloudflare Workers/Vercel Cron
* **안 쓴 것**: 직접 운영하는 서버의 cron, AWS Lambda + EventBridge, Cloudflare Workers Cron Triggers, Vercel Cron.
* **안 쓴 이유**: 전부 별도 계정·배포 설정·(일부) 비용이 필요함. Actions는 저장소 안에 YAML 하나로 끝남.
* **얻은 것**: 설정 30줄, 비용 0, 로그가 Actions 탭에 남음.
* **포기한 것**: 실행 시각이 정확하지 않음(수십 분 지연이 흔함). 러너당 실행 시간 제한이 있어 상세 요청을 300건으로 끊어야 하는 제약과도 맞물림. 비공개 저장소로 바꾸면 무료 분량 제한이 생김.

## 4. 배포: GitHub Pages vs Netlify/Vercel/Cloudflare Pages
* **안 쓴 것**: Netlify, Vercel, Cloudflare Pages.
* **안 쓴 이유**: 빌드가 없는 프로젝트라 이들의 강점(빌드 훅, 미리보기 배포, 엣지 함수)을 쓸 데가 없음. Pages는 저장소 설정 한 번이면 `docs/`가 그대로 올라감.
* **포기한 것**: 커스텀 도메인·리다이렉트·헤더 설정이 제한적. PR 미리보기가 없어 화면 변경은 로컬에서 확인해야 함.

## 5. 화면: Vanilla JS vs React/Vue/Svelte
* **안 쓴 것**: React, Vue, Svelte, 그리고 그에 딸린 Vite·webpack 빌드.
* **안 쓴 이유**: 화면이 "목록 + 필터" 하나. 상태가 필터 객체 하나뿐이라 프레임워크의 상태 관리가 줄 이점이 없고, 빌드가 생기면 Pages에 올리기 전 단계가 하나 늘어남.
* **얻은 것**: 파일 3개(HTML, CSS, JS), 의존성 업데이트 없음, 로딩 즉시.
* **포기한 것**: 화면이 커지면 `app.js` 한 파일이 금방 복잡해짐. 지금 270줄인데 재단별 보기 같은 두 번째 뷰가 들어가면서 이미 분기가 늘고 있음. 컴포넌트 재사용이 `<template>` 하나뿐임.

## 6. 스타일: 직접 쓴 CSS vs Tailwind/Bootstrap
* **안 쓴 이유**: Tailwind는 빌드가 필요하고(CDN 버전은 프로덕션 비권장), Bootstrap은 이 화면에 비해 너무 큼. 240줄이면 손으로 관리 가능.
* **포기한 것**: 디자인 토큰을 직접 정해야 하고, 다크 모드 같은 걸 넣으려면 변수부터 다시 설계해야 함.

## 7. 폰트: Pretendard CDN vs 시스템 폰트/Noto Sans KR/셀프 호스팅
* **선택**: jsDelivr CDN의 Pretendard Variable dynamic subset.
* **안 쓴 것**: 시스템 폰트만 쓰기(가장 가볍지만 OS마다 한글 렌더링 편차가 큼), Noto Sans KR(굵기 변화가 덜 자연스러움), 셀프 호스팅(저장소에 폰트 파일 수 MB가 들어감).
* **포기한 것**: 프로젝트의 유일한 외부 의존. CDN이 죽으면 `font-family` 폴백(Apple SD Gothic Neo, Malgun Gothic)으로 넘어가 모양이 달라짐.

## 8. 개인화: localStorage vs 계정/BaaS
* **안 쓴 것**: Firebase·Supabase 같은 BaaS로 로그인과 동기화.
* **안 쓴 이유**: 사용자가 사실상 한 명. 계정이 생기면 비밀번호·개인정보 책임이 생김.
* **포기한 것**: 기기 간 동기화 없음. 폰에서 넣은 관심 어린이집이 PC에는 없음. 브라우저 데이터를 지우면 사라짐.

## 9. 재게시 중복: 수집 단계 제거 vs 화면에서 묶기
* **고른 것**: 수집 단계에서 가장 최근 글만 남김.
* **안 고른 것**: 데이터는 그대로 두고 화면에서 묶어 "재게시 N회"로 표시.
* **얻은 것**: 데이터가 깨끗해져 이후 모든 기능(통계, 재단별 보기)이 단순해짐. 화면 코드는 안 건드림.
* **포기한 것**: "이 어린이집이 얼마나 자주 재게시하는가"라는 정보가 사라짐. 이게 구인난의 신호일 수도 있는데 지금은 볼 수 없음. 또 묶음 기준(제목·직종이 완전히 같을 때)이 엄격해서 제목을 한 글자만 바꿔 올리면 여전히 두 개로 보임.

## 10. 직종: 수집 단계에서 보육교사만 vs 필터로 남겨두기
* **얻은 것**: 목록이 절반으로 줄고, 상세 요청 예산이 전부 보육교사 공고에 쓰임.
* **포기한 것**: 범용성. 보조교사를 찾는 사람에게는 이제 쓸모가 없음. 다른 직종이 필요해지면 `common.py`의 목록 한 줄과 화면 필터를 되살려야 함.
